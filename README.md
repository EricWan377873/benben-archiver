以下是 GPT 写的介绍

**Benben Archiver** 是一个运行在浏览器开发者工具 Console 中的犇犇历史本地备份脚本。

它用于在犇站等采用相同页面结构的洛谷犇犇保存站中，将指定用户的历史犇犇批量提取为结构化 JSON，并保存到本地。

脚本不调用隐藏 API，也不会通过 `fetch`、XHR 等方式直接批量请求页面。翻页和读取 Markdown 源码均通过模拟正常网页操作完成。

## 主要功能

脚本会自动从当前页面地址识别用户 UID 和当前页码，因此不需要手动修改代码中的用户编号，也没有写死总页数。

例如，可以分别从：

`/user/377873/1`

或：

`/user/377873/23`

启动。

从第 23 页启动时，脚本会备份**第 23 页至最后一页**；从第 1 页启动，则相当于备份该用户当前可访问的全部历史记录。

对于每一条犇犇，脚本保存以下三项数据：

```json
{
  "id": 8658090,
  "time": "发送于 2026/8/30 21:18:04，保存于 2026/8/30 21:18:30",
  "info": "Markdown 源码"
}
```

其中：

* `id`：犇犇编号，例如 `#8658090`；
* `time`：网站记录的发送时间和保存时间；
* `info`：通过网页的“查看 Markdown 源码”功能取得的原始 Markdown 内容。

Markdown 中的多行文本会被正确保留。在最终 JSON 文本中，换行会按照 JSON 标准自动表示为 `\n`，不会因为复制或序列化而破坏原始内容。

## 自动翻页与末页判断

Benben Archiver **没有把“62 页”或任何其他总页数写死在代码中**。

处理完当前页面后，脚本会检查当前已经渲染的 HTML，寻找形如：

`/user/<当前 UID>/<页码>`

的分页链接。

然后筛选所有**大于当前页码**的页面，并选择其中页码最小的一页作为下一页。

例如当前为第 1 页，而分页栏中存在：

`1　2　3　4　5　62`

脚本会选择第 **2** 页，而不是直接跳到第 62 页。

如果当前 HTML 中已经找不到任何大于当前页的合法页码，则认为当前页是最后一页，结束备份。

因此总页数无论是 8 页、62 页还是以后发生变化，都不需要修改脚本。

最后一页也不要求必须有固定数量的犇犇。脚本按照页面中实际检测到的犇犇卡片数量工作，因此最后一页只有 1 条、7 条、49 条等情况均可正常处理。

## Markdown 源码获取方式

脚本不会根据页面显示出来的正文自行推测 Markdown。

对于每一条犇犇，它都会：

1. 找到对应的“查看 Markdown 源码”按钮；
2. 调用该网页元素的 `.click()`；
3. 等待网站自己的 Markdown 源码对话框打开；
4. 从对话框的 `<pre><code>` 中读取源码；
5. 关闭对话框；
6. 继续处理下一条。

因此获得的是保存站自己提供的 Markdown 源码。

## 网络请求频率分析

需要区分“脚本进行了多少次操作”和“实际向线上服务器发送了多少次请求”。

### 1. 初始页面

运行脚本前，用户需要自己正常打开一个用户历史页面。

这个页面本身的加载属于浏览器正常产生的线上请求。脚本启动以后不会重新请求当前页面。

### 2. 翻页

每处理完一页，脚本会实际点击网站分页栏中的下一页按钮。

因此，从第 `S` 页开始，一直处理到第 `E` 页时，脚本会进行：

**E - S 次翻页**

例如从第 1 页处理到第 62 页：

**61 次翻页操作**

每次翻页都可能触发保存站前端正常加载下一页所需要的网络请求。具体一次翻页对应几个 HTTP 请求，是由网站自身的 SvelteKit 前端实现、缓存状态以及浏览器行为决定的，脚本本身没有将它固定为某个请求数量。

因此，从“加载线上页面数据”的角度看，可以近似理解为：

**每处理完一页，最多进行一次正常的下一页导航操作。**

脚本不会提前并发加载几十页，也不会一次性向服务器发送 62 个页面请求。

### 3. “查看 Markdown 源码”

每条犇犇都会点击一次“查看 Markdown 源码”。

但是，**点击一次不等于一定产生一次网络请求**。

从页面结构来看，Markdown 源码最终由网站自己的对话框显示；脚本只是点击网站已有按钮并读取结果。至于点击按钮时网站是从当前已经加载的数据中直接取得 Markdown，还是临时向服务器请求 Markdown，需要由网站前端实际运行时的行为决定。

脚本本身没有主动执行：

`fetch(...)`

`XMLHttpRequest`

或直接访问某个 Markdown API。

所以更准确地说：

**每条犇犇产生一次 Markdown 源码查看操作；如果网站本身需要联网取得源码，该操作会产生网站自己的网络请求；如果源码已经存在于前端数据中，则不会因此新增线上数据请求。**

脚本在每条记录之间还设置了约 **80～160 ms** 的随机间隔，并在打开 Markdown 按钮前加入少量等待，以避免在极短时间内连续操作页面。

### 4. 翻页间隔

每次进入下一页并确认新页面已经渲染以后，脚本还会额外等待约：

**250～500 ms**

再继续工作。

因此它不是将所有页面同时并发爬取，而是严格按照：

**当前页 → 逐条读取 → 下一页 → 逐条读取 → 下一页……**

的串行方式运行。

### 5. 不会产生的请求

脚本本身不会：

* 使用 `fetch` 批量下载用户历史；
* 使用 XHR 调用保存站接口；
* 直接构造并请求后续 2、3、4……页 URL；
* 并发请求大量历史页面；
* 根据犇犇 ID 直接请求隐藏 API；
* 将抓取结果上传到其他服务器。

它对线上数据的访问依赖于网站原有界面操作。

## 数据输出

每处理完一页，Console 都会立即输出这一页的 JSON，例如：

```json
{
  "page": 23,
  "data": [
    {
      "id": 1234567,
      "time": "发送于 ……，保存于 ……",
      "info": "……"
    }
  ]
}
```

因此即使处理大量历史记录，也可以观察每一页的进度和结果。

运行期间还提供：

`window.__BENBEN_ALL__`

用于查看截至当前已经收集的全部数据。

`window.__BENBEN_LAST_PAGE__`

用于查看最近完成的一页。

最终完成后：

`window.__BENBEN_RESULT__`

保存完整 JavaScript 对象，而：

`window.__BENBEN_RESULT_JSON__`

保存已经通过 `JSON.stringify()` 序列化的完整 JSON 字符串。

## 自动保存到本地

全部页面处理完成后，脚本会自动生成一个 `.json` 文件并通过浏览器下载到本地。

例如从 UID `377873` 的第 1 页开始：

`benben-377873-from-page-1.json`

如果从第 23 页开始：

`benben-377873-from-page-23.json`

文件名会明确标记备份是从哪一页开始的，避免将部分历史误认为完整历史。

整个备份文件只在本地生成。脚本没有将整理后的 JSON 上传至服务器的功能。

## 中途停止与数据保留

运行过程中可以随时在 Console 输入：

```javascript
window.__BENBEN_STOP__ = true
```

脚本会请求停止后续处理。

已经成功读取的数据仍然保存在：

```javascript
window.__BENBEN_ALL__
```

中。

如果脚本因为网页加载异常、DOM 变化或其他错误中断，已经读取成功的数据同样不会因为主循环异常而立即丢失，可以从该变量中取回。

## 兼容性

Benben Archiver 不把 `benben.sbs` 域名写死为抓取目标，也不把某一个用户 UID 写死在代码中。

因此，它原则上可以用于采用相同前端结构的其他犇犇保存站。

它主要依赖以下页面约定：

* 用户历史地址采用 `/user/<UID>/<页码>`；
* 每条犇犇存在 `/feed/<ID>` 形式的链接；
* 每条记录存在发送时间和保存时间；
* 页面提供“查看 Markdown 源码”功能；
* Markdown 源码通过网页自身的对话框展示；
* 分页以 `/user/<UID>/<页码>` 形式提供。

如果另一个保存站只是域名不同，而仍然采用这一套前端结构，通常无需修改脚本。

如果另一个站虽然也保存犇犇，但 URL、DOM、分页或 Markdown 查看方式不同，则需要针对该站调整相应的 DOM 选择器和页面识别逻辑。

## 一句话概括

**Benben Archiver 通过模拟用户在保存站上逐条查看 Markdown、逐页点击分页按钮的方式，将从当前页开始的用户犇犇历史完整整理成 JSON，并在浏览器本地保存。**
